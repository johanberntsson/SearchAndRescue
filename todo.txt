WHERE IT IS

A flyable voxel engine: 160x152 3D view over a six-row text panel, 14.2 fps
(PROFILE=0, default map sizes). No game yet.

Build knobs, all in the Makefile:
    PROFILE=0            no per-column instrumentation; use it for timing
    WIDE=1               render all 320 pixels instead of stretching 160
    HGT_SIZE, COL_SIZE   map resolutions, powers of two from 256 to 1024

Where a frame goes (160 wide, h256 c512, 64.7 ms; the shape is the same at
other settings):

    ray march                  46.0 ms   71%   10240 samples at 182 cycles
    terrain span fills         10.0 ms   15%   14489 pixels at ~28
    span prologues              3.4 ms    5%   3983 colour reads
    per-column C setup          2.4 ms    4%   607 cycles a column
    sky DMA                     2.1 ms    3%
    panel and everything else   0.8 ms    1%

Every column takes all 64 samples -- none terminates early -- so the march is
flat in the scene and scales only with COLUMN COUNT. That one fact governs
most of the trades below.

NEXT

**The renderer is good enough for a game.** Called on 9 Aug 2026, comparing a
fresh screenshot against the first one: clearly more detail, and faster than
it started. The optimisation ideas left in OPEN below are there so they are
not rediscovered from scratch, NOT as a queue to work through -- the next
work is the game, not another few percent.

- controls: joystick and keyboard. Long push -> big speed change, short push
  -> small, accelerating towards a target speed rather than jumping to it.
  Joystick forward/back and left/right, cursor keys to rotate the drone.
  Scale the acceleration by the measured frame time: between 7 and 15 fps a
  per-frame constant will not feel the same twice.
- then the game itself. documentation/vision.md has the design; nothing of it
  exists yet.

DECISIONS ALREADY SETTLED (do not re-litigate without new measurements)

- Detail per cycle lives in the MAP, not in the raster. 320-wide rendering
  doubles the march and halves the frame rate for a picture that barely
  changes; a finer colourmap is free and plainly better. WIDE=1 is kept as an
  option, off by default, and its real argument is the 40-column panel.
- Colourmap resolution is free at any size: read once per span, and the plane
  lookup is one `lda abs,x` whether there are 4 planes or 16.
- Heightmap above 256x256 costs a flat 5.7 ms (8.8%) because it leaves chip
  RAM -- the SAME at 512 or 1024. So h1024 is no slower than h512; it just
  cannot share a d81 with c1024 (1013 KB against ~793 KB).
- Rendering into attic RAM and DMAing the frame back is DEAD: attic-to-chip
  DMA is 17.8 cycles a byte against 2.45 chip-to-chip, so one 320x152 buffer
  would be 21 ms a frame. The writes were never the problem (+3 cycles).
- A pre-rendered sky in attic RAM is dead for the same reason. The chip-RAM
  strip template costs 2.1 ms; from attic it would be 13.5.
- ADCQ for the ray position is SLOWER (68.5 ms against 64.7). The Q
  pseudo-register is A/X/Y/Z, so it destroys the march's step index in Y.

OPEN

- the far edge of each z band pops as you fly. Either blend the bands or
  shorten the step growth.
- no pitch control, and the horizon is fixed. vx_horiz is already rebuilt
  whenever cam->horizon moves, so the renderer is ready for it.
- the panel is 20 columns, which is what 160 pixels of 8-pixel characters
  gives. 40 needs WIDE=1, or a raster split that changes CHRXSCL below the
  3D view -- which would get the wider panel without paying for the march.
- no HUD over the 3D view. vision.md wants an artificial horizon, battery,
  GPS and signal strength. Palette 240/241 are reserved for it; hud.c did
  exactly this kind of pixel drawing and is in git history if wanted back.
- an overview map in the panel, a small version of the colour map. It cannot
  be text characters; it wants full-colour cells, which can be mixed into the
  panel per cell since the mode is chosen by character number.
- 1024x1024 for BOTH maps needs a second disk, or a packed format better than
  exomizer's 1.9-2.2x on this data.
- remaining march ideas, all small: the per-column C setup is 607 cycles and
  two mul_shift8 calls; the position update is 40 of the 182 cycles a sample.

DONE

- calypsi toolchain, d81 build with autoboot.c65, resources as SEQ files
- minimal voxel engine, 160x192 double buffered, ASWD/RF to fly
- profiler (src/profile.c, tools/profread.py) with a raster-calibrated clock,
  plus micro-benchmarks in src/bench_asm.s and an on-screen report for real
  hardware, which has no -dumpmem
- 0.74 -> 10.3 fps: the compiler's 32-bit multiply was 64% of the frame; the
  hardware multiplier and then an assembly inner loop did the rest
- attic RAM measured on real hardware: a read is a flat +16 cycles, a write
  +3, attic-to-chip DMA 7.3x slower than chip-to-chip
- sky by DMA, 10.3 -> 11.3 fps. One strip template, FB_COLS copy jobs, and it
  doubles as the frame's clear pass
- split screen, 11.3 -> 12.6 fps. 19 rows of 3D over a 6-row text panel;
  hud.c gone. Needed CHARPTR set and panel ink moved into the first sixteen
  palette entries, because a text character's colour is a four-bit field
- inner loop, 302 -> 182 cycles a sample, 12.6 -> 15.5 fps, output
  pixel-identical: carried the write pointer between spans, moved the
  position's whole-cell bytes into the map pointer, biased the height
  difference positive
- 320-wide rendering behind WIDE=1
- exomizer compression (src/exo_asm.s, ported from mega65/ozmoo-z6) unpacking
  into attic RAM, and both map resolutions as build knobs up to the source
  1024x1024
